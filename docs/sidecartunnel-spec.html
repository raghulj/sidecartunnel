Design specification  ·  draft 1

Sidecartunnel

A standalone websocket gateway for applications that cannot hold long-lived connections themselves. It terminates sockets, authorizes subscriptions against grants your application issues, and fans messages out across replicas. It never learns your domain model.

Runtime single static Go binary Bus Redis pub/sub (pluggable) Integration HTTP + HMAC, any language

01 What it is, and what it refuses to be

Request/response runtimes — WSGI, Rack, PHP-FPM, CGI — cannot hold thousands of open sockets. The usual escapes are to bolt an async server onto the side of the app, or to rent a hosted realtime service. The first couples your realtime layer to one framework's event loop; the second puts a vendor between you and your own users.

Sidecartunnel is the third option: a process that owns the sockets and speaks ordinary HTTP to the application. The application publishes by making a POST. It authorizes by answering a question or signing a token. It never imports a websocket library, never runs an event loop, and never changes its deployment model.

Non-goals

  • Not a message broker. No durable queues, no delivery receipts, no dead-letter handling. Your database is the source of truth; this is an accelerator in front of it.
  • Not an identity provider. No user table, no login, no password, no session store.
  • Not a policy engine. It holds no rules about who may see what, because it holds no concept of what anything is.
  • Not a peer-to-peer relay. Clients never message each other without the application in the path.

Each of those is a feature. They are the reason the whole thing fits in a few thousand lines and can be reasoned about in an afternoon.

02 The principle everything follows from

Load-bearing

The gateway enforces. The application decides. Every authorization answer originates in the application and reaches the gateway as either a signed token or an HTTP response. The gateway's entire security model is: verify a signature, then match a string.

This is not an aesthetic preference. Any realtime layer that re-derives "who may see this" has become a second copy of your authorization rules, written in a different language, deployed on a different cadence, by someone reading your schema from the outside. The two copies will drift, and the drift will be silent — it produces no error, only a message delivered to the wrong person.

So the gateway is given grants, never facts. It is told "this connection may subscribe to room-*", not "this user belongs to team 42". It cannot tell you what a team is, and that is precisely what makes it reusable across applications that disagree about everything else.

Throughout this document, gateway marks what sidecartunnel owns and application marks what stays yours.

03 Topology

04 Four contracts

The entire product is four interfaces. Everything else is implementation detail you should be able to replace without telling anyone.

gateway◄──►browser

C1 · The client protocol

JSON frames over a single websocket. The first frame must be connect; the token travels in the frame body, never the query string, because query strings survive in access logs, proxy logs, and browser history.

client → gateway
{"id": 1, "connect": {"token": "<jwt>", "subs": ["room-9182", "user-7"]}}
{"id": 2, "subscribe": {"channel": "room-4410"}}
{"id": 3, "unsubscribe": {"channel": "room-9182"}}
{"ping": {}}
gateway → client
{"id": 1, "connect": {"client": "8f2c...", "ping": 25, "subs": {...}}}
{"push": {"channel": "room-4410", "pub": {"data": {...}, "offset": 91}}}
{"id": 2, "error": {"code": 103, "message": "permission denied"}}
{"disconnect": {"code": 3501, "reason": "token expired", "reconnect": true}}

Multiplexed: one socket carries every channel, with an integer id correlating replies to commands. Server-initiated pings on a fixed interval, client pongs; a missed pong closes the connection so half-open sockets behind a NAT or a load balancer get reaped rather than accumulating.

The browser client is roughly 200 lines: connect, exponential backoff with jitter, a subscription registry it replays after a reconnect, and an event emitter. It ships as a dependency-free ES module.

application──►gateway

C2 · Publishing

An ordinary HTTP POST, authenticated by an HMAC over the body and a timestamp. The secret never crosses the wire, so a leaked log line or a compromised TLS-terminating proxy does not hand over publish rights, and a captured request cannot be replayed outside a narrow window.

application → gateway
POST /api/publish
X-St-Key:       app_live_7f3a
X-St-Timestamp: 1756612800
X-St-Signature: hex(HMAC_SHA256(secret, timestamp + "." + body))

{"channels": ["room-4410"], "event": "message.created",
 "data": {"id": 88123, "body": "..."}, "exclude_client": "8f2c..."}

exclude_client suppresses the echo to the connection that originated the action, so the sender's own optimistic UI is not overwritten by its own event.

EndpointPurpose
POST /api/publishOne event to one or many channels
POST /api/broadcastBatched publishes in a single round trip
GET /api/channelsOccupied channels and subscriber counts
GET /api/presence/{ch}Current members of a presence channel
POST /api/disconnectImmediate revocation — drop a user's connections everywhere

Roughly fifteen lines to implement in any language, which is the point: the protocol is the product, and a client library is a convenience rather than a dependency.

gateway──►application

C3 · Identity and authorization

Three modes, all producing the same internal structure. An application picks whichever fits how it already authenticates; the gateway cannot tell them apart afterwards.

Mode A — token minted by the application

The application signs a short-lived token with the shared secret and hands it to its own frontend however it already passes data — a template variable, a JSON endpoint, a meta tag.

token claims
{
  "sub":      "user-7",
  "info":     {"name": "Ada", "avatar": "/u/7.png"},
  "channels": ["room-4410", "room-9182", "user-7", "org-42-*"],
  "exp":      1756616400,
  "jti":      "01J8..."
}

The whole trick

The channels claim is a list of glob patterns the application computed using its own authorization code. The gateway matches strings against it. It does not know what org-42 denotes, cannot enumerate valid orgs, and holds no rule that could disagree with the application's — because it holds no rule at all.

Mode B — cookie-forward, no token at all

For applications that would rather not mint anything, the gateway forwards the browser's Cookie and Origin headers to an endpoint you expose. The application resolves its own session exactly as it does for any other request and answers with the same shape.

gateway → POST /_st/connect  ·  application responds
{"sub": "user-7", "info": {...},
 "channels": ["room-4410", "user-7"], "expires_in": 3600}

This is the mode most existing applications should use. It requires no frontend auth code whatsoever — no token endpoint, no refresh plumbing — and costs one HTTP call per connection, not per message. For a session-cookie application the integration is a single view function.

Mode C — per-subscribe callback

Some grants cannot be enumerated in advance: membership that is a database fact, or a set too large to embed in a token. Enabled per namespace, the gateway asks once per subscription and caches the answer for the life of the connection.

gateway → POST /_st/subscribe  ·  application responds
→ {"sub": "user-7", "channel": "room-77123", "client": "8f2c..."}
← {"allow": true, "info": {"role": "moderator"}}

Expiry, refresh, revocation

Grants are a snapshot, so they need an end. Before a token expires the gateway asks the client to refresh; the client fetches a new one, or Mode B re-runs the webhook. If the application now answers differently, the connection is closed. For immediate revocation — an account suspended, a member removed — POST /api/disconnect propagates over the bus and every replica drops that user's sockets. Together these give revocation without an authorization check on the message path.

gateway◄──►gateway

C4 · The bus

One narrow interface, so the transport is a deployment choice rather than an architectural one.

internal/bus
type Bus interface {
    Publish(ctx context.Context, channel string, payload []byte) error
    Subscribe(ctx context.Context, channel string) error
    Unsubscribe(ctx context.Context, channel string) error
    Receive() <-chan Message
}

Two implementations at launch: memory for single-node and tests, redis for everything else. A replica subscribes upstream only for channels it actually holds locally, and drops the upstream subscription when the last local subscriber leaves — so a Redis instance carries traffic proportional to active channels, not to the total number ever created.

Redis holds no connection state. Presence, when enabled, is the single exception: a hash per channel with TTL'd members, refreshed by the owning replica.

05 Channels and namespaces

A channel is an opaque string. A namespace is the prefix before the first separator, and it selects a block of configuration. This is how per-feature behaviour gets expressed without per-application code: a new feature is a config block, not a release.

sidecartunnel.yaml
namespaces:
  - name: public              # anyone connected may subscribe
    auth_required: false

  - name: room                # a grant must match
    auth_required: true

  - name: chat                # membership is a database fact
    auth_required: true
    subscribe_callback: true  # Mode C
    history_size: 100
    history_ttl: 5m

  - name: desk                # who is online, who is typing
    auth_required: true
    presence: true
    join_leave: true

So chat-9182 resolves to the chat namespace and inherits its policy. Channels stay human-readable on purpose — they appear in logs, in metrics labels, and in the gateway's own introspection endpoints. Opaque or encoded channel names buy nothing (a name is not a secret, and authorization is what protects the channel) while costing you every ability to debug a delivery problem.

06 Delivery semantics

At-most-once, stated plainly. A replica restart, a network partition, or a client that was asleep will drop messages. Building at-least-once into the bus means durable per-subscriber cursors, acknowledgements, and redelivery — a broker, with a broker's operational weight, which contradicts everything in section 01.

The pattern that makes this a non-problem

The application already persists whatever it publishes. So the client reconciles rather than the bus guaranteeing: on every reconnect, fetch ?since={last_seen_id} and merge. Realtime becomes an accelerator over a database that was always the source of truth — which survives replica restarts, laptop sleep, tunnels, and multi-hour disconnections alike, none of which any redelivery scheme handles well.

For applications that want to skip the reconnect fetch, a namespace may enable bounded history: a capped Redis stream per channel, with an offset and an epoch so a client can detect that its position was trimmed away and fall back to a full resync. Treat it as an optimization for the common short disconnection, never as durability.

Slow consumers

Every connection has a bounded outbound queue. On overflow the connection is closed with a code instructing the client to reconnect and resync — never blocking the fan-out path. This single rule is what keeps one client on a bad train connection from stalling delivery for everyone else in the channel, and it is where naive implementations of this pattern fail.

07 Inside the binary

layout
cmd/sidecartunnel/       entry point, flags, signal handling
internal/config/         YAML + env, namespace rules, app credentials
internal/proto/          frame encode/decode, error codes
internal/client/         one connection: reader, writer, subscriptions
internal/hub/            sharded channel registry, local fan-out
internal/bus/            Bus interface + memory and redis implementations
internal/auth/           token verify, HMAC verify, grant matching
internal/webhook/        connect and subscribe callbacks, with timeouts
internal/api/            the HTTP surface from C2
internal/presence/       members, TTL refresh, join/leave
internal/metrics/        prometheus collectors

Per connection: one reader goroutine, one writer goroutine, one buffered outbound channel. The hub is a sharded map — 32 shards, each with its own mutex — because a single lock over every channel is the first thing to melt under a broadcast storm, and sharding is a twenty-line fix that never needs revisiting.

Grant matching happens on the connection's own goroutine against an in-memory slice of patterns. No lock, no network call, no allocation on the hot path.

08 Running it

A static binary in a scratch image, around 12 MB. No runtime, no interpreter, no sidecar of its own. Configuration by YAML file or environment variables, exhaustively — nothing requires a rebuild.

ConcernBehaviour
ScalingStateless replicas. No sticky sessions — any replica serves any client.
Load balancerIdle timeout must exceed the ping interval, or the proxy reaps healthy sockets.
Rolling deploysGraceful drain: stop accepting, send disconnect with reconnect: true, let backoff spread the reconnect storm.
Health/health liveness, /ready gated on bus connectivity.
Observability/metrics: connections, subscriptions per namespace, publish latency, dropped-slow-consumer counter, webhook error rate.
Multi-appSeveral (id, key, secret) triples per instance, fully isolated. One gateway can serve unrelated applications.

That last row is worth separating from a word it collides with: multi-app isolation is the gateway's tenancy, and it has nothing to do with tenancy inside your application. Whether your app has one customer or ten thousand is invisible here, and must stay that way — the moment the gateway models your tenants, section 02 is broken.

09 Scope

v1 — build

  • C1 client protocol, C2 publish API
  • Auth modes A and B
  • Redis and memory buses
  • Namespace config, glob grants
  • Refresh, disconnect, drain
  • Metrics, health, browser client

v2 — once proven

  • Mode C subscribe callback
  • Presence and join/leave
  • Bounded history with offsets
  • Channel lifecycle webhooks
  • SSE fallback for locked-down networks

Never

  • Message persistence
  • An identity or user store
  • Client-to-client without the app
  • Domain concepts of any kind
  • An admin UI beyond introspection

Presence sits in v2 deliberately. It is the one feature that makes the gateway stateful, and it should not be built until the stateless core has run in production long enough to be boring.

10 Open decisions

Is Mode B the default in the documentation?

Cookie-forward requires no frontend code and suits the target audience — session-based server-rendered applications — but it puts an HTTP call in the connection path and requires the gateway to reach the application. Mode A is faster and looser but pushes token plumbing onto every integrator. My inclination is to lead with B and present A as the optimization.

Bidirectional, or receive-only?

Client-to-server messages could ride the socket, but the application must persist and validate them anyway, so the gateway would only be forwarding to an HTTP endpoint the client could have called directly. Receive-only over the socket, send over ordinary HTTP, keeps validation, rate limiting, and moderation in code you already trust — at the cost of one extra request per send.

How much does the client library carry?

Reconnect and resubscribe are non-negotiable. Presence state, history replay, and offset tracking could live in the library or be left to the application. The larger it gets, the more it becomes a framework — and the harder it is for anyone to write a second implementation in another language.
